WHY & LEARN

CLOUD ENGINEER · 신입

송진하

전체 흐름을 먼저 파악하고, ‘왜?’를 품고 근거로 설계하며, 꾸준히 배우고 성장합니다.

멀티클라우드 교육 프로젝트에서 웹 서비스 구성과 CI/CD 파이프라인 구축을 경험했습니다. 서비스의 요구사항을 기준으로 기술의 장점과 한계를 살피고, 구성요소의 연결부터 구축 이후의 운영까지 함께 고민합니다.

01 강점

제가 일하는 방식.

01

꾸준함과 책임감

목장과 유가공 사업을 하며 365일 하루도 빠짐없이 소를 돌봤습니다. 살아 있는 생명을 돌보는 일은 미루거나 건너뛸 수 없고, 하루의 소홀함이 곧바로 결과로 돌아옵니다. 그 시간 동안 누가 보지 않아도 해야 할 일을 매일 끝까지 해내는 태도를 몸에 익혔습니다.

02

전체를 보는 시야

전체 서비스의 흐름을 파악하고, 그 안에서 담당 영역을 바라봅니다. 구성요소 사이의 연결과 의존성을 이해하고, 하나의 선택이 다른 영역에 미치는 영향까지 고려합니다.

03

‘왜?’로부터 시작되는 설계

‘왜 이 기술이 필요한가?’를 먼저 묻습니다. 요구사항을 기준으로 대안들의 비용과 운영 부담, 안정성을 비교하고, 선택의 이유와 한계, 보완 방법까지 설계에 담습니다.

04

Learn & Grow

어떤 상황에서도 배울 점을 찾습니다. 시행착오를 겪으면 원인을 분석해 같은 문제가 반복되지 않도록 재발 방지책을 마련하고, 그 과정에서 얻은 배움을 다음 시도에 반영합니다.

02 소개

현장에서 쌓은 운영 경험을 클라우드로 이어가고 있습니다.

목장과 유가공 사업, 교환·반품센터 운영을 경험했습니다. 교환·반품센터에서 업무 흐름을 파악하고 운영 기준을 정리했던 경험을 바탕으로, 클라우드 프로젝트에서도 구축 이후의 운영을 함께 고민했습니다.

베스핀글로벌 멀티클라우드 교육에서 두 차례 팀 프로젝트를 수행했습니다. 중간 프로젝트에서는 AWS 기반 서비스의 Web/WAS/DB 구성을 맡았습니다. 최종 프로젝트에서는 AWS·GCP 환경에서 팀 전체를 이끌며 CI/CD 파이프라인을 구축하고, 실제 서비스 운영을 가정해 배포를 진행했습니다. 교육과 프로젝트에서 배운 내용을 실제 서비스 환경에서 검증하며 역량을 넓혀 가고자 합니다.

중간 프로젝트 · 3-TIER

Spring PetClinic · AWS 3계층 웹 서비스

2026.06.30 – 07.13 · 팀 AWSome 5명 · AWS 3계층(Web · WAS · DB)
프로젝트 기록 자세히 읽기 ↗

담당 역할: 서비스 리소스(Web · WAS · DB)

Web · WAS · DB의 역할을 분리한 AWS 환경에 Spring PetClinic을 배포하고, 고가용성을 목표로 서비스를 구성했습니다. 저는 서비스 리소스(Web · WAS · DB)를 맡아 Apache · Tomcat 구성, PetClinic 배포·연결, Aurora 읽기·쓰기 연결 분리를 위한 소스 코드 수정과 DB 인스턴스 사양 구성을 담당했습니다.

요청 흐름

사용자 → 외부 ALB → Apache → 내부 ALB → Tomcat · PetClinic → Aurora

내 역할 · 구현 내용
OK

Web 요청 중계 구성 — Apache에서 내부 ALB로 요청을 전달하도록 구성했습니다. WAS 사설 IP에 직접 연결하던 방식에서 내부 ALB를 경유하도록 변경해 인스턴스 증설·교체에 대응했습니다.

OK

WAS · PetClinic 배포 및 DB 연결 소스 수정 — Tomcat에 PetClinic을 배포하고, 애플리케이션 소스 코드를 수정해 Aurora Writer/Reader 연결을 분리했습니다. 트랜잭션 속성에 따라 연결 대상을 선택하도록 라우팅을 구현했습니다.

OK

DB 인스턴스 구성 — 리소스 사용량을 기준으로 DB 인스턴스 사양을 구성했습니다.

WAS 메모리 부족 대응
  1. 발생t3.micro 기반 WAS 점검 중 메모리 사용량이 늘며 OOM과 응답 지연이 발생했습니다.
  2. 판단(추정)조회 건수에 제한이 없는 조회 로직이 메모리 부담을 키웠을 것으로 판단했습니다.
  3. 조치WAS를 t3.micro에서 t3.small로 변경하고, JVM 힙을 512m에서 768m으로 조정했습니다.
  4. 재검증같은 시험 조건에서 안정적인 동작을 확인했습니다.
팀 검증 결과
  • 자동 확장·축소 — Web·WAS Auto Scaling의 최소·희망·최대 인스턴스를 각각 2/2/4대, CPU 목표를 40%로 설정하고 확장·축소를 검증했습니다.
  • 인스턴스 장애 대응 — 인스턴스 종료 시 ASG가 대체 인스턴스를 생성하는 것을 확인했습니다.
  • 가용성 확인 — 같은 AZ의 Web·WAS 인스턴스를 동시에 중단했을 때 다른 AZ에서 서비스가 유지되는 것을 확인했습니다.
  • 배포 전환·롤백 — 내부 ALB 대상 그룹의 수동 전환을 통한 Blue/Green 배포와 롤백을 검증했습니다.
  • DB 장애 조치 비교 — 반복 시험 중 각 DB의 최대 관측 서비스 복구 시간은 Aurora 17초, RDS 약 35초였습니다.
  • 백업 복원 — PITR로 DB를 특정 시점으로 복원하고, 복원 기준 시점의 데이터와 대조했습니다.
  • 권한 분리 — 태그 조건을 적용한 IAM 권한 분리를 검증했습니다.
  • 보안·모니터링 — WAF 차단과 CloudWatch → Discord 알림을 검증했습니다.
최종 프로젝트 · CI/CD · DR

Retail Store · AWS 운영 & GCP 재해복구

2026.08 – 10 · 팀 AWSome 5명
프로젝트 기록 자세히 읽기 ↗

AWS(EKS · RDS)에서 쇼핑몰을 운영하고 완료 주문을 GCP(GKE · Cloud SQL)에 복제해, 장애 시 승인 후 전환하는 환경을 구성했습니다. CI/CD(이미지 빌드·게시, AWS Argo CD 수동 Sync)와 함께, AWS 리전 장애에 대비한 GCP 재해복구(DR) PoC를 맡아 복구 환경 구성과 전환 검증을 담당했습니다.

  1. AWS 운영EKS · RDS에서 쇼핑몰 운영
  2. 주문 데이터 복제RDS → GCP Cloud SQL (Cloud DMS)
  3. 승인 후 전환장애 시 Slack 승인 → DB 승격 · DNS 변경
  4. GCP에서 처리GKE로 요청 처리, AWS 중단 상태에서 확인
내 역할 · 검증 근거
OK

이미지 빌드 · 게시 — GitHub Actions로 검사·빌드, ECR · Artifact Registry 게시

OK

AWS Argo CD 수동 Sync — 승인한 배포 입력을 수동 동기화로 반영

OK

경로 정렬 — GCP 설정 경로와 CI 검사 경로 불일치 수정 (9/22 커밋)

OK

GCP 재해복구(DR) PoC — GKE 복구 환경·Cloud DMS 복제 구성, 승인(Slack → DB 승격·DNS) 후 전환해 AWS 중단 상태에서 정상 처리 확인

팀 검증 결과
  • 배포 상태 확인 — 리소스 27개의 Synced/Healthy 상태와 5개 서비스의 Pod 10개 준비 상태를 확인하고, 데모 주문과 재로그인 후 주문 조회까지 확인했습니다(9/16).
  • 앱 교체와 상태 유지 — 로그인 세션과 Checkout 상태를 외부 저장소(Valkey)에 두고, Pod를 교체한 뒤에도 상태가 유지되는 것을 확인했습니다.
  • 캐시 장애 전환 — Valkey 주 노드 장애 전환 후에도 서비스가 정상 동작하는 것을 확인했습니다.
  • 혼합 부하 — 최대 100 VU·피크 10분 유지 조건에서 HTTP 79,282건 중 실패 0건, 전체 p95 71.50ms, 주문 20/20건 완료를 기록했습니다.
  • 주문 데이터 복제 — RDS의 주문 데이터를 Cloud SQL로 복제해 순차 주문 50/50건 반영(9/7)과 이후 표본 주문·복제 지연을 확인했습니다.
  • 승인 후 DR 전환 — Slack 승인 후 DB 승격·DNS 변경으로 전환해, 전환 자동화 시작부터 실제 GCP 연결까지 200.601초(약 3분 21초)를 관측했습니다(9/23).

※ 300명은 목표(미실시), 일부 검사 실패 존재, 200.601초는 관측값으로 공식 RTO 아님
