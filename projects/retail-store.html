멀티클라우드 CI/CD와 DR

01

배경과 목표

애플리케이션을 배포하는 것에서 더 나아가, 어떤 소스가 어떤 이미지가 되어 어느 환경에서 실행되고 있는지 설명할 수 있는 운영 흐름을 만들고자 했습니다. 팀은 완료 주문의 보호를 우선하는 DR 구조를 설계했습니다. 최종 목표는 RTO 120분, Orders RPO 1분, 연간 가용성 99.7%였으며 목표값과 실제 시험에서 확인한 범위는 별도로 관리했습니다.

02

시스템과 저장소

App 저장소 → 이미지 CI → ECR · GAR
                           ↓
             GitOps 배포 버전 / 환경 values
                           ↓
           AWS Argo CD 수동 Sync → Pod 확인

주 운영 환경: AWS EKS · RDS PostgreSQL
DR 환경: GCP GKE · Cloud SQL

서비스는 UI·Catalog·Cart·Checkout·Orders의 5개 구성요소로 나뉩니다. AWS EKS와 RDS PostgreSQL을 주 환경으로 사용하고, GCP GKE·Cloud SQL로 주문 데이터와 서비스 전환을 준비했습니다.

  • App 저장소: 애플리케이션 소스, Dockerfile, 이미지 CI와 서비스 버전
  • Infra 저장소: Terraform·Terragrunt, 클러스터·IAM·환경 입력
  • GitOps 저장소: Helm 차트, 환경별 values, 배포 버전, Argo Application과 운영 절차
03

나의 담당 영역

CI/CD에서는 서비스별 빌드·게시 조건, AWS OIDC 인증 진단, Helm 렌더 검사, AWS/GCP 설정 입력 검증, Argo CD 설치·배포 연결과 릴리스 인계 문서를 중심으로 작업했습니다. namespace·ServiceAccount·Secret·서비스 연결을 함께 검사해, 각 담당자가 만든 구성요소가 배포 단계에서 맞물리도록 했습니다.

AWS 리전 장애에 대비한 GCP 재해복구(DR) PoC도 맡았습니다. GKE 복구 환경에 서비스를 배포하고, Cloud DMS로 RDS의 주문 데이터를 Cloud SQL에 복제하도록 구성했습니다. 장애 시에는 Slack 알림 후 담당자 승인을 거쳐 DB 승격과 DNS 변경이 실행되도록 했고, AWS를 중단한 상태에서 전환한 뒤 서비스 요청이 정상 처리되는 것을 확인했습니다.

DMS 접속정보 갱신처럼 DB 복제 구성 중 다른 팀원이 맡은 작업, 전체 인프라와 APM 계측은 개인 성과에 포함하지 않습니다. DR 시험의 전환 시간 측정은 06 팀 검증 결과에 따로 적었습니다.

04

릴리스 구현 과정

구현 1. 한 번 빌드한 이미지의 게시와 추적

App 변경과 버전 입력을 바탕으로 대상 서비스 이미지를 빌드하고 ECR·GAR에 게시하는 흐름을 구성했습니다. 게시 성공 여부만 보지 않고 서비스별 태그, 소스 SHA, Actions 실행, digest를 함께 인계했습니다. 두 클라우드에서 사용할 이미지의 내용이 같은지 추적할 수 있도록 한 것입니다.

구현 2. GitOps 입력과 정적 검증

GitOps에서 환경 values와 서비스 버전 입력을 관리하고 Helm 렌더 결과를 검사했습니다. AWS/GCP의 namespace, Secret 참조, Service 연결과 같은 계약을 배포 전에 확인했습니다. 로컬 검사 통과와 GitHub CI 실행 결과를 구분했고, 정적 검사 성공을 실제 GCP 배포 성공으로 바꾸어 기록하지 않았습니다.

구현 3. 수동 Sync와 배포 후 확인

이미지 게시 이후 GitOps 버전 변경과 Argo CD 수동 Sync를 거쳐 배포하도록 연결했습니다. 이미지 자동 업데이트·GitOps 자동 PR·자동 Sync까지 구현한 완전 자동 배포는 아닙니다. 배포 시에는 대상 revision과 상태를 확인하고, 실행 중인 Pod imageID를 게시된 digest와 대조했습니다.

대표 사례인 9월 30일 UI v0.1.8 배포에서는 소스 SHA → Actions → ECR·GAR digest → GitOps PR → Argo revision → Pod imageID → 화면 배지를 연결한 기록을 남겼습니다.

05

문제 해결 기록

문제 해결 1. 배포 이름과 selector 불일치

GitOps의 Application·releaseName과 실제 설치된 Helm release 이름이 달랐습니다. namespace만 맞추면 된다고 가정하지 않고 Deployment selector·Service 대상·소유권 연결을 함께 확인했습니다. PR #9에서 이름을 retail-store로 정합화하고 후속 배포 기록으로 연결했습니다.

문제 해결 2. Sync 후 사라진 관측 도구 배치 조건

실제 클러스터에만 남아 있던 WhaTap의 MGMT 배치 조건이 Sync 이후 사라지는 문제를 확인했습니다. PR #11에 nodeSelector·toleration을 AWS values로 반영해 선언적 원본에 보존했습니다. 후속 Sync에서는 master가 MGMT에서 Running이고 node agent 4개가 APP·MGMT 노드에 Running인 상태를 확인했습니다. 관측 설계 전체가 아니라 배포 조건의 보존·통합 작업입니다.

문제 해결 3. 관리 컴포넌트의 숨은 의존성

Argo CD를 MGMT 노드로 옮겨도 CoreDNS·metrics-server의 기존 배치 조건 때문에 APP 노드가 필요했습니다. 관리 컴포넌트의 nodeSelector를 바꾸는 것과 운영 의존성 전체를 독립시키는 것은 다르다는 점을 확인했습니다. 9월 29일 기존 Argo 배치 변경에서는 7개 Pod Ready와 내부 health 200을 확인했지만, 새로운 환경에서 최초 설치하는 경로의 완전한 재현까지 성공한 것은 아닙니다.

06

팀 검증 결과

목표와 관측값을 구분합니다. 다음 결과는 팀의 특정 시험 조건에서 얻은 값이며, 운영 SLA나 모든 기능의 성공을 의미하지 않습니다.

DR 시험에서는 9월 23일 Workflow 시작부터 실제 GCP 접속 전환까지 약 3분 21초를 관측했습니다. 이 수치는 장애 발생부터 전체 업무가 복구되기까지의 공식 RTO가 아닙니다. 9월 11일 Cutover부터 전체 주문 흐름 복구까지는 36분 41초였고 당시 30분 목표는 충족하지 못했습니다. 측정 구간이 달라 두 숫자로 개선율을 계산하지 않습니다.

10월 2일 최종 보존 부하 보고서의 mixed100은 최대 100 VU, 피크 유지 10분, 주문 시도 최대 20건 조건에서 HTTP 요청 79,282건·HTTP 오류 0건·전체 HTTP p95 71.50ms·완료 주문 20건을 기록했습니다. 다만 카트 표시 검사 1건 실패와 Carts Pod 3개 Pending이 남았고, 별도 auth50 시험은 실패했습니다. 따라서 전체 기능 성공, 300명 처리 검증, 자동 확장 완성으로 설명하지 않습니다. 이 결과는 팀 시험 결과이며 제가 모든 튜닝과 측정을 단독 수행한 성과는 아닙니다.

07

회고와 개선 방향

  • 배포 성공 메시지보다 소스·산출물·선언·실행 상태가 서로 연결되는 증거가 중요했습니다.
  • Git에 없는 운영 변경은 다음 Sync에서 유실될 수 있어, 필요한 설정은 선언적 원본으로 되돌려야 합니다.
  • 승인 운영 규칙과 플랫폼의 기술적 강제 설정은 다릅니다. 모든 변경에 두 사람 승인이 강제되었다고 주장하지 않습니다.
  • 배포 후 기능 확인, 변경 기록의 보존, 신규 설치 재현, 장애 감지부터 복구까지의 측정 기준을 더 일관되게 만드는 것이 후속 과제입니다.
  • RDS Multi-AZ·전체 Failback·격리 Restore 시험과 300명 부하는 완료된 성과가 아닙니다.
